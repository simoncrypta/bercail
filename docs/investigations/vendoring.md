# Vendoring

**Proposal**, for bercail-x0ey. Checked on 2026-11-20 against
[`eb2ac33`](https://github.com/simoncrypta/bercail/commit/eb2ac33) (v0.18.0), and
against each upstream's `main` on the same day. Nothing here is built yet.

Recommendation: keep vendoring by copy, with the record beside each copy, and add
a `git:` source to the dependency tracker so that a moved upstream opens a
`vendor` issue. Do not use the alternatives. Submodules ship empty in the tarball
installs and block `bercail cleanup`. Subtree commits before review, which the
staged review in tuicr does not allow for. A fetched pin keeps upstream's code out of
the staged diff.

## The options

Four ways to hold upstream code, measured against how bercail is built and installed.

**Submodule.** bercail's history stays smallest, but the rest breaks:

- Installs from a tarball ship it empty. The release archive is `git archive HEAD` (`.github/workflows/release.yml:36`), and the curl install unpacks GitHub's `/archive/<tag>.tar.gz` (`lib/common.sh:149`). Neither includes a submodule's files, so curl, mise and packslip installs would come without pi-emphasis or the statechart skill. Fixing that changes the release workflow and the install path, which are both high stakes.
- A clone install, and the Omarchy hook that fast-forwards it (`config/omarchy/bercail.hook:25`), would also need `git submodule update --init`.
- Each new worktree starts with an empty submodule folder until someone initializes it, and worktrunk does not. Once it is initialized, `bercail cleanup` refuses the worktree (`lib/cleanup.sh:38-41`), because `git worktree remove` refuses a worktree with initialized submodules.
- A submodule takes a whole repo. For the statechart skill that is all of cursor/plugins, with the test corpus bercail leaves out, and bercail's own four files could no longer sit among upstream's.
- In review, a move shows as a changed gitlink (`Subproject commit a → b`), so tuicr shows none of upstream's code. An agent's edit inside the submodule shows only as a dirty marker, not as lines anyone reviews.

**Subtree.** Its files are ordinary files in bercail's tree, so tarballs, clones, worktrees and cleanup work unchanged. The costs are elsewhere:

- `git subtree add` and `pull` need a clean tree and make their own commits: a merge, plus a squash commit with `--squash`. bercail's review is a staged, uncommitted tree in tuicr, and Shep commits after the person's look. A subtree move arrives already committed, and can be reviewed only as a diff against the commit before it. Its bookkeeping lives in the commit message (`git-subtree-dir`, `git-subtree-split`), so restaging it with `reset --soft` would lose the base the next pull needs.
- It takes a repo or a split. For the statechart skill, every move would mean `git subtree split --prefix=pstack/skills/statechart` in a clone of cursor/plugins first, and the license sits outside that prefix. The split brings `scripts/test/`. If bercail deletes it, upstream changes to the tests become modify/delete conflicts, and both recent upstream commits change tests. bercail's `SKILL.md` replaces upstream's, so upstream changes to it risk conflicts too.
- For pi-emphasis, the whole repo would land in `bstack/pi/extensions/pi-emphasis/`, README and `package.json` included, while bercail ships two files.
- Without `--squash`, upstream's history for the path joins bercail's. With it, each move adds two commits.
- Its one real strength is a three-way merge of local edits to upstream files. bercail makes none to its git upstreams, by rule. The copies that are edited heavily, the Herdr mods, have no git upstream for subtree to merge from.

**Fetched pin** (a URL, a commit and a sha256 in the tree, downloaded at deploy, like TLC):

- A move is a changed hash, so tuicr shows none of the code that will run. The `how` and `why` skills cannot read it in the repo either. The review step that pi-emphasis's `UPSTREAM.md` asks for (look for a new import, network call, shortcut or prompt section) would happen outside review.
- Deploy needs a new download step in the install path, which is high stakes. Deploying from a clone or a package would add a download whenever nothing is cached, and the live tests would need the network or a fake.
- bercail's statechart scripts import upstream's modules (`graph.ts` reuses upstream's parsers), so the download would have to be laid over bercail's files, unless the skill is rearranged.
- `pi install git:` was already rejected (`bstack/pi/extensions/pi-emphasis/UPSTREAM.md`): it runs npm in a clone and writes to the person's own Pi settings.

**Copy with a record** (today):

- Ordinary files, so every install path, worktree and cleanup works, and agents need to know nothing new.
- A move is a staged diff of upstream's actual changes, reviewed line by line in tuicr, the same as any other change. Review is better here than with any of the other three.
- History holds only the bytes at each move.
- Upstream files are not edited by rule, and bercail's own files sit beside them. `tests/pi_emphasis.bats` enforces the rule for pi-emphasis's `index.ts`. Nothing enforces it for the statechart skill.
- What it lacks: nobody is told when upstream moves (`source: none` only lists the copy in the tracker's run summary), and a move is done by hand.

## The notifier

The dependency tracker already has the plumbing a vendor notifier needs: a daily
scheduled run (`.github/workflows/deps.yml`), one issue per entry found by its
`deps:<name>` label, and the failing-lookup issue. What it lacks is a feed for a
commit. Its release logic stays as it is: version tags, `sort -V`, the stable-release
gate, and the day's wait for mise. Add one source kind to `.github/scripts/deps-track.sh`,
with its own comparison, and change the two git entries in `lib/deps.json`:

```json
{
  "name": "pstack-statechart",
  "source": "git:cursor/plugins",
  "paths": ["pstack/skills/statechart", ":!pstack/skills/statechart/scripts/test", "pstack/LICENSE"],
  "known": "3dbd22ff12742fb28c9700b9760baa29ed41dc13",
  "pinned_in": ["skills/statechart/UPSTREAM.md"],
  ...
}
```

`paths` holds the git pathspecs bercail copies, so a commit that only changes upstream's
tests opens nothing. Without `paths`, the whole repo counts. pi-emphasis would be
`"source": "git:johnlindquist/pi-emphasis"` with `"paths": ["index.ts", "LICENSE"]`.

For a `git:` entry, `check` would:

1. Make a single-branch, blobless clone with no checkout, from `https://github.com/<owner>/<repo>` (the tests point the base at a local repo). Not a shallow one: the check needs the old pin and its ancestry. No code from the clone runs.
2. Fail the lookup when `known` is not an ancestor of the default branch's tip, which means upstream rewrote its history or `known` is wrong.
3. Take the target: the newest first-parent commit in `known..tip` that touches `paths`. None means the copy is current, even when `known` is not the last commit to touch `paths`: a move may pin the tip itself. On cursor/plugins today, the tip `d42aff0` is not an ancestor of the last statechart commit `0b46ec3`, so comparing against that commit would reject a good pin.
4. When there is a target, open or update one issue titled `vendor: <name> <full target sha>`, labelled `deps`, `deps:<name>` and `vendor` (created first, like the other labels). Keeping `deps` lets the open-issue listing and the failure issue stay as they are. A new target retitles the issue and comments on it. Close the issue when its target is `known` or an ancestor of it. A target missing from the clone is a failed lookup, not a reason to close.
5. Write a body that holds `git log --oneline known..target -- <paths>` (the upstream PR numbers show in the subjects), `git diff --stat known target -- <paths>`, a compare link with the full shas, and `pinned_in`. The steps for a move stay in the copy's `UPSTREAM.md`, and the body points there.

Use git here, not the GitHub API. GitHub's
[compare](https://docs.github.com/en/rest/commits/commits#compare-two-commits) lists at
most 300 files: for `3dbd22f...0b46ec3` it returned 300, where git counts 315. The
clone's 2 MB does not bound the run, because `--stat` fetches the blobs it compares.

The tracker would not cover these copies:

- The Herdr mods and layout. Their upstream is the Herdr app, not a git repo. The `herdr-app` entry opens an issue on each Herdr release, and its notes say to check the mod copies. `doctor_mod_copies` says on each machine when an installed mod has moved, but nothing checks the layout. Whether Herdr's release artifacts expose the mods for CI to compare was not checked.
- The Entire extension. The `entire` entry opens an issue on each CLI release, and rerunning `entire enable --agent pi` rewrites the file.

None of these gets a `vendor` issue with a diff. Whether that is enough is Simon's call.

## First step

One change, with no edit to `.github/workflows/`. `deps.yml` already runs
`deps-track.sh check` daily with `contents: read` and `issues: write`, and cloning a
public repo needs no token.

1. In `.github/scripts/deps-track.sh`, add the `git:` source and `paths` as above, and extend `check_pins`'s shape check to allow them.
2. In `lib/deps.json`, move `pstack-statechart` and `pi-emphasis` to `git:` sources.
3. In `tests/statechart.bats`, check that `UPSTREAM.md`'s commit is `lib/deps.json`'s `known`, as `tests/pi_emphasis.bats` does for pi-emphasis.
4. In `tests/deps_track.bats`, cover the new source against a local upstream repo made in the test: moved; current at a later tip whose `paths` did not change; a test-only commit ignored; a license-only commit noticed; a rewritten history; a target superseded; and an issue closed once `known` reaches its target. Check each body and its labels, not only which writes ran.
5. Add the `git:` source and the `vendor` label to the tracker section of `docs/development.md`.

Taking pstack's `0b46ec3` into the copy is a separate job.

The script writes issues, but `.bercail/policy.toml` marks only `.github/workflows/`,
not `.github/scripts/`, as high stakes. Simon may still want to review it before it
lands.
